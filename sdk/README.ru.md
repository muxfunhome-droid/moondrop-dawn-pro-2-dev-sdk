# SPV4040 SDK — свои программы на C для ЦАПа

**Язык:** [English](README.md) · Русский


> **⚠️ ПРОЕКТ НАВАЙБКОЖЕН: ВСЁ СДЕЛАНО НЕЙРОСЕТЬЮ. ВСЁ НА ВАШ СТРАХ И РИСК.** Подробности — в главном `README.md`.

Программа на C встраивается в заводскую прошивку как дополнение: аудио, USB, эквалайзер и кнопки
работают как прежде, а ваш код получает `app_init()` при старте и `app_loop()` на каждом проходе главного цикла.

## Быстрый старт
```sh
scripts/build_app.sh rainbow build/fw_custom2.bin build/fw_rainbow.bin
# то же самое: python3 -I sdk/spv_build.py sdk/examples/rainbow --base build/fw_custom2.bin -o build/fw_rainbow.bin --emu
```
Скрипт скомпилирует программу, вставит её в `fw_custom2.bin`, пересчитает checksum и прогонит результат
в эмуляторе. Печатаются журнал `spv_log()` и цвета, которые программа выставила на LED.
Получившийся `fw_rainbow.bin` прошивается через `spv_flasher.html`, как обычно.

Новая программа: создайте папку с `*.c`, подключите `#include "spv.h"` и определите `app_init` / `app_loop`.

Нужен `riscv64-unknown-elf-gcc` (Debian: `sudo apt install gcc-riscv64-unknown-elf`).

## Первый запуск на железе
1. Прошейте **`fw_sdk_empty.bin`** (пустая программа `examples/empty` поверх `fw_custom2.bin`).
   ЦАП должен вести себя точно как с `fw_custom2.bin`. Это проверяет механизм крючков, RAM по `0x130000` и `mcycleh`.
2. Только потом прошивайте `fw_rainbow.bin` и свои программы.
3. Держите под рукой дамп flash или `fw_custom2.bin` для отката.

## Как это устроено
| Что | Где |
|---|---|
| Код и константы программы | flash `0x48020c00…0x48037000` (~89 КБ), за кодом прошивки и заглушками LED |
| `.data` / `.bss` | RAM `0x130000…0x13a000` (40 КБ). Прошивка занимает `0x100000…0x122000`, стек — вниз от `0x140000` |
| Стек | общий с прошивкой |
| Вход при старте | `0x48002d88`: `jalr ra,0xf4` (init прошивки) → `jal __spv_init_hook` |
| Главный цикл | `0x48002d8c`: `jalr ra,0x360` → `jal __spv_loop_hook` (тело `0x360` переписано на C в `rt/spv_rt.c`) |

`__spv_init_hook`: init прошивки → копирование `.data` / обнуление `.bss` → `app_init()`.
`__spv_loop_hook`: аудио-задача прошивки `0x1138` → заводская задача LED (если LED не захвачен программой) → `app_loop()`.

В начале образа программы лежит заголовок `SPVA` с исходным размером секции CPU. Поэтому `spv_build.py`
может взять базой уже собранный образ: старая программа удаляется (база восстанавливается байт в байт) и ставится новая.

Флаги компиляции: `-march=rv32imafc_zicsr -mabi=ilp32f -mno-relax -Os`. ABI совпадает с прошивкой, поэтому её
функции можно вызывать напрямую. `gp` принадлежит прошивке (`0x106c18`), а `-mno-relax` и отсутствие
`__global_pointer$` гарантируют, что ваш код его не трогает. Стандартной библиотеки нет: в рантайме есть
`memcpy/memset/memmove/memcmp/strlen`, плюс `libgcc` (64-битное деление и т.п.).

## API (`include/spv.h`)
- **Время:** `spv_millis()`, `spv_micros()`, `spv_cycles()`, `spv_cpu_hz()` (360 МГц по эмулятору).
  Блокирующие `spv_delay_ms/us()` — функции прошивки, в `app_loop` только короткие.
- **Светодиод:** `spv_led_claim(true)` отключает заводскую логику LED. Дальше `spv_led_rgb(r,g,b)` задаёт настоящий цвет
  (общий анод учтён и не зависит от патчей `--invert`), `spv_led_off()` гасит. `spv_hsv_to_rgb()`.
  `spv_led_claim(false)` возвращает LED прошивке.
- **Состояние прошивки:** `SPV_EQ_PRESET` (8 = обычный режим), `SPV_LED_EVENT`, `SPV_LED_ENABLED`, `SPV_USB_STATE`.
- **Прочее:** `spv_reboot_to_bootloader()`, `spv_fw_adc_read()` (ручки/кнопки, семантика не разобрана), регистры `SPV_PAD()`, `SPV_REG32()`.
- **Журнал:** `spv_log("x=%d %08x %s\n", …)` пишет в кольцевой буфер в RAM. Его показывает эмулятор (`--emu`).

## Правила
- `app_loop()` не должен блокировать: в том же цикле обрабатываются аудио и HID-команды прошивки,
  включая команду «войти в загрузчик», через которую идёт перепрошивка. **Зависший `app_loop` = нельзя
  перепрошить штатно.** Способ войти в загрузчик без работающей прошивки пока неизвестен.
- Пишите машины состояний на `spv_millis()` вместо `while(…)` и длинных задержек.
- Перед прошивкой всегда прогоняйте `--emu`. Эмулятор не моделирует прерывания, USB-хост и аудио, поэтому
  нужные состояния выставляйте в RAM сами (см. `emulate()` в `spv_build.py`).
- Код, вызванный из обработчиков прерываний (например, перехваченная аудиофункция), может использовать float: обработчики
  прошивки сохраняют caller-saved регистры FPU и fcsr. Он не должен блокировать, а прерывания прошивки вложенные
  (таймер/кнопки могут прервать аудио), поэтому обменивайтесь данными через простые переменные с одним писателем.

## Проверено на железе
`fw_rainbow.bin` (радуга на LED поверх `fw_custom2.bin`) прошит и работает идеально. Тем самым подтверждены: исполнение кода
с `0x48020c00`, запись и чтение RAM по `0x130000`, `.data`/`.bss`, `mcycle/mcycleh`, `spv_millis()`, `spv_led_rgb()`,
`spv_led_claim()`, подмена вызовов в `main()` прошивки.
Также на железе работает `examples/bubble` (перехват аудио и кнопок). Не проверено: `spv_log` (буфер в RAM виден только эмулятору), `spv_fw_adc_read`, `spv_reboot_to_bootloader` из своей программы.

## Примеры `examples/calc` и `examples/life` — ПК ↔ чип по USB HID
Оба перенаправляют заводской обработчик vendor-HID `0x8d84` через `spv_ram_redirect()` и используют свой байт команды в отчёте 75
(`0xCA` калькулятор, `0xCB` «Жизнь»); все остальные отчёты уходят в заводской код, так что перепрошивка работает.
Ответ отправляется функцией прошивки `0x8418(ctx, buf, 64)`; она сразу копирует данные в FIFO эндпоинта, так что буфер может быть любым.
`life` показывает, как делать долгие вычисления без блокировки: обработчик только копирует запрос, счёт идёт в `app_loop()` порциями,
ответ — когда всё готово. У каждого примера есть программа для Linux в `host/` и `test_emu.py`. Подробности — в их README.

## Пример `examples/bubble` — свой звук и бульки на кнопках ✅ на железе
```sh
scripts/build_app.sh bubble build/fw_custom2.bin build/fw_bubble.bin
python3 -I sdk/examples/bubble/test_emu.py       # bit-exact с заводским EQ, кнопки, рендер build/bubble_demo.wav
```
- Функция EQ прошивки `0x1668` (её зовёт USB-прерывание на каждый аудиопакет) перенаправлена на `bubble_eq()` через
  `spv_ram_redirect()`: заводской EQ (бит в бит) + эффект «warm» (бас +4 дБ, кроссфид, мягкий ограничитель).
- Колбэки кнопок «+»/«−» подменены прямо в RAM-структурах MultiButton: PRESS_DOWN → бульк (у «+» выше, у «−» ниже),
  LONG_HOLD → бульк на каждый шаг громкости, DOUBLE_CLICK «−» → вкл/выкл эффекта, смена режима EQ → двойной бульк.
  Подробности — `docs/ARCHITECTURE.md` §10.
- Бульк синтезируется внутри аудиопотока, поэтому слышен, только пока хост шлёт звук.
- Параметры звука (`FX_*`, `BUB_*`) — в начале `main.c`.

`spv_ram_redirect(addr, orig0, orig1, fn)` — новый вызов SDK: заменяет первые 8 байт RAM-функции прошивки прыжком в `fn`
(аргументы и адрес возврата сохраняются; исходные слова проверяются). Код, вызванный из обработчиков прерываний, может
использовать float (обработчики прошивки сохраняют FPU), но не должен блокировать. Прерывания прошивки вложенные.
